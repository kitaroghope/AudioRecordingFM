Expert UI Review

Feedback & usability audit of the scheduling interface

A source-level review of the Prime Radio recording scheduler, focused on the two things that decide whether an interface feels trustworthy: how it tells you what just happened, and how easily you can get a schedule saved.

The visual design is genuinely good and the server error contract is well built. But the client-side feedback layer is not delivering what the backend already sends — four defects break the core "add a program" journey, one of them a security issue. All four are small, contained fixes.

The core journey, broken

Adding a program is the one thing this page exists to do. Marked steps are where the current build loses the user.

Current behaviour 4 breaks
  1. Fill in the form Days, start/end time, program name.
  2. Validation → modal alert Errors arrive as a popup, not next to the field that caused them.
  3. Confirm dialog Button labels silently fail to change — this renders as No / Yes.
  4. "You need to be logged in" The auth check runs after confirmation. The user retypes everything.
  5. Save → success alert Stacks a second dialog on top of the first: "add another?"
  6. List does not update The new program is missing from Scheduled Programs until a manual reload.
Recommended behaviour 0 dead ends
  1. Auth checked up front Page nudges to log in before any work is done, not after.
  2. Inline field validation Red hairline + message under the exact field. Screen reader announces it.
  3. Confirm with real labels Buttons read Cancel and Add program — never Yes/No.
  4. Save with inline progress Button shows "Saving…" and disables; no ambiguity.
  5. One success message An inline confirmation banner. No stacked modal dialogs.
  6. List refreshes in place New card animates in, form stays filled for the next entry.

Critical findings

Four defects on the primary path. Each has been confirmed by reading the source, not inferred.

C1
Confirm and Alert dialogs are visually identical — the labels never change
Critical

The defect

script.js relabels the dialog buttons via $('#btnClo') and $('#btnAcc') — but the markup defines id="modal-no-btn" and id="modal-yes-btn". The two IDs do not exist anywhere in the project, so every jQuery write is a silent no-op.

The result: a destructive "are you sure?" confirmation and a passive success notice both present as No / Yes.

Why it matters

"Yes" carries no meaning. On a confirmation the user must read the body text to know what they are agreeing to — recognition has collapsed into recall. This is also the direct cause of C4 and H1.

Fix

Replace both IDs with the real ones, then give the dialog a proper mode: customConfirm renders Cancel / Add program, customAlert renders a single Close.

script.js:249-250, 268-269 · try.html:330, 334
C2
The login requirement is discovered after the user has already filled the form in
Critical

The defect

The isLoggedIn() check sits at line 548 — after the confirmation dialog is awaited at line 544. The user selects days, sets times, types a name, clicks Add, reads the confirmation, presses Yes… and only then learns they must log in.

The form state survives the interrupt, but the flow has been reset to zero confidence.

Why it matters

Auth is a precondition, not a validation error. Checking preconditions after the expensive part of the task is the single most common cause of abandoned flows.

Fix

Move the check to the top of captureData(), before any validation. Better still, gate the Add button itself and show a "Log in to add programs" prompt in place of the form while logged out.

C3
The scheduled-programs list never refreshes after a successful save
Critical

The defect

fetchRecordedPrograms() is called exactly once, on page load. The success branch after /newProgram never calls it — instead it clears the form and asks "Would you like to add another program?"

Answering No does window.location.href = '/try.html' — a full page reload used as a substitute for a refetch. Answering Yes leaves the stale list on screen entirely.

Why it matters

The app reports success for work whose result is invisible. The user has no on-screen confirmation that their program actually exists — the core promise of the page is unverified. It also throws away scroll position and re-downloads the whole bundle.

Fix

Call await fetchRecordedPrograms() on success and drop the reload. Let the form keep its values so repeat entry is one keystroke from the next program.

try.html:493 (only call) · try.html:589-602 (success path)
C4
One global promise slot — a second dialog strands the first forever
Critical

The defect

Every dialog writes to a single module-level variable, dialogResolveFunction. There is no queue and no stack. If a second dialog opens while the first is awaiting, the resolver is overwritten and the first promise never settles.

Nothing times out, so the awaiting code blocks silently — and the Add button stays disabled with no way out but refreshing.

Why it matters

This is a hang, not a cosmetic bug. Because C1 means alerts and confirms are indistinguishable, users clicking buttons quickly is the expected path — exactly the sequence that triggers it.

Fix

Resolve any pending promise with false before storing a new one, and add a focus trap + Escape handler so a dialog always has exactly one dismiss path. Consider a proper dialog component instead of hand-rolled modal CSS.

H1
The session-expired message promises an action that never happens
High

The defect

On a 401 the error text reads "Click OK to log in now". No such button exists — the button renders as "Yes" (C1), and clicking it only closes the dialog. Nothing opens the login modal.

Fix

Either open showLoginModal() directly from the 401 branch, or drop the sentence. Silently broken instructions are worse than none.

try.html:571
H2
Unescaped program names rendered into innerHTML, with the auth token in localStorage
High

The defect

formatProgramCard() interpolates program.prog and each day name directly into an innerHTML template string with no escaping. The server sanitises names on write, but the card trusts that data on read.

Any path that stores an unsanitised name — a manual database edit, a future import, a legacy row — becomes stored XSS. And because authToken lives in localStorage, injected script can exfiltrate it directly.

Why it matters

This is the one finding with a security dimension, and the two halves compound: an XSS sink plus a token in a JS-readable store means a stored name could hand over a live session.

Fix

Render with textContent or a DOM-building helper instead of string HTML — the daysBadges span list is a trivial createElement loop. Sanitise on write as defence in depth, not as the primary control.

try.html:429-449 · script.js:10-13
H3
Both modals are inaccessible — no role, no focus trap, no Escape, no focus return
High

The defect

A project-wide search returns zero aria-* attributes and zero role= attributes. Neither dialog declares role="dialog" or aria-modal; there is no focus trap, no Escape handler, no initial focus placement, and no restore on close.

A keyboard user can Tab straight out of the open dialog into the page behind it. A screen reader announces no dialog at all.

Fix

Add role="dialog" aria-modal="true" aria-labelledby, trap Tab within the panel, close on Escape, and return focus to the trigger. The :focus-visible ring in style.css is already there — it just needs a focusable container to live in.

try.html:95-182, 300-341 · style.css:61-64
H4
The Tips card promises editing that does not exist
High

The defect

The tips list states "You can edit programs after adding them." Program cards are display-only — no edit, no delete, no toggle. A /deleteProgram route exists server-side and is never called by any frontend file.

Why it matters

A wrong instruction is a small lie the app tells about itself. And without any management affordance, a mistaken schedule can only be corrected by finding a database admin.

Fix

Add edit and delete to each card with a confirm-and-undo pattern, or delete the bullet until it is true. Wiring the existing /deleteProgram route is most of the work already done.

try.html:283 · app.js:265
H5
A normal cold start renders as a red error state
High

The defect

/recordedPrograms returns a bare {} before the startup read completes — the catch block on failure also returns {}. The client then evaluates data.listings.length, which throws on undefined, and lands in the catch that renders "Failed to load programs" in red.

Why it matters

An ordinary, temporary condition is reported as a failure. Users who see a red error on first paint conclude the app is broken before they have done anything.

Fix

Guard with (data.listings ?? []).length, have the server always return {listings: []}, and add a retry button to the error state — there is currently no way to retry short of refreshing.

What is genuinely working

Worth protecting during any refactor — these are the reasons the rest of the list is fixable rather than a rewrite.

The server error contract

Every failure ships a human-readable message, an optional hint, structured errors, and a meaningful status code — 400/401/409 are all handled distinctly. The client already maps them well. The problem is only that the modal layer throws that detail away.

The empty state

"No programs scheduled yet — Add your first program below" with a clear icon and directional copy. This is a properly designed empty state, and it is better than most production apps manage.

Confirm-before-write

Verifying the schedule before persisting is exactly right for a system that records broadcast audio — a wrong entry silently consumes a recording slot. This instinct is sound; only the dialog's presentation needs work.

Visual discipline

A single rose accent, consistent radii, restrained shadows, a coherent icon set, and a visible :focus-visible ring. The design system is more disciplined than the feedback layer — which is why the polish reads well at a glance.
